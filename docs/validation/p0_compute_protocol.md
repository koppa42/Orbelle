# 独立计算吞吐量协议

本协议在实现和首次测量前固定工作量、计时边界和有效性检查。它测量当前公开 C++ 接口的单进程、单调用线程吞吐量，与双视图图形场景分开。尚未约定吞吐量或资源上限，不据此宣布性能验收通过。

## 工作量

`baseline` 固定为下表；`smoke` 只用于构建与内存检查，不能作为性能基线。每项先运行 1 次预热，再运行 5 次测量；smoke 为 1 次预热、2 次测量。顺序固定，不随机化，不将顺序差异解释为精确的性能因果关系。

| case ID | baseline 工作量 | smoke 工作量 | 单位 |
|---|---|---|---|
| `application_sample` | 10,000 个 Session × 601 个公共历元 | 8 × 7 | CartesianState |
| `frame_build` | 601 个历元各求 EOP 和完整状态变换 | 7 | StateTransform |
| `frame_apply` | 已生成的 6,010,000 个状态应用相应历元的完整变换 | 56 | CartesianState |
| `spice_scalar` | 日、月相对地球，各 10,000 次单次查询 | 各 16 | EphemerisState |
| `spice_batch` | 相同日月与历元，分别一次批量调用，共 20,000 个状态 | 共 32 | EphemerisState |
| `spice_context_switch` | 两个独立 Provider 交替查询，共 200 次 | 8 | EphemerisState |

圆轨道使用 GCRF XY 平面解析案例，不代表通用二体、J2 或真实星座。对象索引 i 从 0 开始：半径 `7,000,000 + (i % 10) × 1,000 m`，μ=`3.986004418e14 m³/s²`，参考历元为 `-i` TAI 秒；每个 Session 使用独立对象 ID、revision=1。公共请求历元为 Epoch 0 起逐秒 0…600（smoke 0…6），输出顺序为对象优先、历元次之。

参考系使用 `iers_c04_2000_01_01_2000_01_02` 本地快照、现有 ERFA Provider、完整 `Rv + R_dot*r`，每个公共历元只建立一次变换。复用的是计算层的同历元变换，没有使用图形缓存、插值状态或显示精度。`frame_build` 包含 EOP 查询和变换构建；`frame_apply` 单独衡量变换应用。

CSPICE 使用 `de440s_2016_leap` 的冻结 LSK/SPK，target=10/301，observer=399，J2000，几何状态，无光行差改正，速度对 TDB 秒求导。请求从快照的 first_epoch 起每 60 TAI 秒一次。scalar 与 batch 输出都是先全部日状态、再全部月状态。context_switch 的第 i 次请求用 Provider `i % 2`，偶数查询日、奇数查询月，历元索引 `i / 2`；第二个 Provider 独立加载同一快照，不伪称两个不同物理模型。每轮开始前激活第二个 Provider，使每个被计时查询都需要切换。每次切换包括当前实现的清空内核池、加载及校验成本，不包括创建 Provider、初始文件复制。所有查询经过现有串行封装；该协议不测多线程扩展性。

## 计时与输出

- 单独创建可选 headless 可执行文件；无 Qt、VSG、Rocky 依赖。baseline 只允许 Release 且关闭 sanitizers 的构建。
- Session、输入历元、Provider 和文件快照创建均在计时之外。每项每轮重建返回结果，计时包含结果容器分配、接口校验、算法和结果元信息。旧结果清空/销毁在下一轮开始计时之前；本轮结果在计时结束后才读取和验证。
- 保留每轮 `steady_clock` 开始/结束纳秒、操作数量和 phase。CPU 时间由 Windows GetProcessTimes 或 Linux CLOCK_PROCESS_CPUTIME_ID 取得，采样边界略宽于墙钟边界；不含结果验证。记录时钟来源和分辨率，不把 CPU 时间除以多核数来假定负载。
- 记录进程累计峰值驻留内存。它包括输入、保留结果、预热和验证，不能当作每项算法的独立内存增量；不为无界面进程虚构 GPU 指标。
- 所有结果均在计时之后完整读取，生成稳定的非密码学 64 位摘要，防止输出未使用。摘要用于同一二进制内重复一致性，不要求不同编译器的浮点比特相同。
- 保存全部原始轮次。只对 5 次测量计算耗时 min/median/max 和 `操作数 / median 耗时`；预热不进入统计。记录可执行文件 SHA-256、源码/协议/数据 SHA-256、Git 提交及工作区状态、构建配置、依赖状态、主机和运行命令。运行前后核对这些输入未变；不允许覆盖旧输出目录。
- 这是预热后的公开接口吞吐量，不是冷启动、硬实时保证、Python 调用性能或独立算法精度验证。scalar 与 batch 的时间均包含各自公开 API 的分配/校验，不能把全部差异归结为 mutex。

## 有效性门槛

沿用已经实现并验证的数值容限，不根据本轮速度结果调整它们。

- 所有状态的历元、原点、参考系、数量、顺序和 provenance 必须正确，所有数值有限。
- 每个圆轨道状态：半径误差 ≤1e-8 m，比能量误差 ≤1e-7 m²/s²，角动量误差 ≤1e-4 m²/s。
- 为防止相位或参考历元被忽略，额外用 `sqrt(μ/r³) × (t+i)` 的解析相位逐状态核对 XY 分量：位置误差 ≤1e-7 m、速度误差 ≤1e-9 m/s。这是固定工作量检查，不能当作独立通用轨道算法验证。
- 每个变换后的状态做正逆往返：位置各分量误差 ≤5e-8 m、速度各分量误差 ≤5e-10 m/s；检查完整矩阵与导数有限、元信息一致。
- 同一二进制各轮输出摘要相同；scalar、batch 和 context_switch 与对应 scalar 状态逐字段一致。这是同实现的接口一致性检查，独立星历和参考系准确性仍由独立的 jplephem/Orekit 交叉校验覆盖。
- 原始报告必须具有全部 6 项、准确轮次/操作数、合法且不重叠的正耗时区间，所有检查成功；缺项、错误 profile、输入变动、非零程序退出或损坏报告不能生成有效吞吐量结论。smoke 的有效性不等于 baseline 的有效性。

数值失败必须保留失败诊断，不能改小工作量、放宽容限或丢弃失败轮次后宣称同一基线有效。

## 算法热点诊断

`orbitforge_algorithm_benchmark` 是单独的显式 Release 目标，不加入普通构建或 CTest 耗时门槛，也不改变上述六项基线协议：

```powershell
cmake --build --preset compute-benchmark --target orbitforge_algorithm_benchmark
$env:PATH = "$PWD/out/dependencies/installed/x64-windows/bin;$env:PATH"
out/build/compute-benchmark/benchmarks/compute/Release/orbitforge_algorithm_benchmark.exe data/samples out/validation/algorithm-before
```

输出目录必须不存在。每项预热一次、测量五次，记录全部墙钟毫秒、中位数和输出摘要。计时包含结果分配及调用，但不含随后对输出的完整读取、摘要和重复一致性检查。工作量固定为：

- 内置 EGM96 20×20：10,000 个固定位置的加速度，以及相同位置的解析引力梯度。
- 约束区间搜索：一天、30 秒发现步长、1 毫秒边界容差，约束为 `sin(0.013 × TAI秒) − 0.2`，保留辅助极值搜索。
- 多对象报告：32 个默认二体卫星、0–600 TAI 秒逐秒采样，共 19,232 行 ITRF 状态；使用固定 `iers_c04_2000_01_01_2000_01_02` 数据，包含会话创建、传播、完整参考系转换和表格构建。
- HPOP：从 `{7e6,0,0}` m、`{0,5000,5600}` m/s 传播一小时，内置 EGM96 20×20、真实 ERFA/IERS、原有默认 RKF78 自适应参数；每轮创建新的传播器，不复用上一轮积分缓存。

比较同机、同编译器和依赖的连续 A/B，至少重复三组；另存 Git 版本、源码、程序与数据散列、主机信息和原始日志。摘要相同只说明该固定负载输出一致，独立精度仍由完整 Release 数值回归及原参考容限验证。此工具不衡量界面、Python 调用、峰值内存或全部轨道模型，不能将局部热点加速等同于整段传播同比加速。
