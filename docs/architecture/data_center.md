# 统一数据中心开发方案

此文记录 2026-10-10 的首版实现及后续方向。已完成 [Scenario 数据锁](scenario_data_lock.md)、SQLite 统一目录、简化的 EOP 管理窗口、IERS finals2000A 全量下载和应用运行期间的自动更新。UTC 时间数据仍为内置只读版本，SPICE、GP/OMM/TLE 尚未接入。

## 管理边界

应用级“数据中心”统一管理数据源、已安装版本、下载任务和更新策略；每个 Scenario 只保存确定版本的引用清单与哈希。第一批覆盖 EOP，随后接入可按实例加载的 UTC 时间数据、SPICE，最后扩展 GP/OMM/TLE。普通用户选择数据类型和来源后即可下载，清单由适配器生成。

数据更新只新增不可变快照。新场景使用已设置的默认版本；已有场景继续使用自己的数据锁，用户显式选择“更新场景数据”后才验证覆盖范围、重建并切换。下载新版本和应用到场景是两个独立动作。

## 存储与引用

桌面使用 Qt `AppLocalDataLocation/data`，Windows 默认 `%LOCALAPPDATA%/OrbitForge/data`，可通过 `ORBITFORGE_DATA_HOME` 指定其他目录。指定目录后不自动搬迁旧目录；导入时仍保留原数据身份。C++/Python 可显式选择目录：

```text
data/
  catalog.sqlite       版本、依赖、默认版本、策略和最近更新状态
  blobs/sha256/...      原始文件，按内容哈希寻址、去重
  snapshots/<lock>/    manifest.json、record.json 及数据文件视图
  staging/...          尚未校验发布的临时下载
```

SQLite schema 1 包含 `snapshots`、`dependencies`、`settings` 三张表。快照目录按依赖清单总哈希命名；record.json 保存清单原始字节的 SHA-256 与依赖身份。数据视图优先使用指向内容文件的硬链接，不支持硬链接时使用经校验的副本。finals2000A 保存整个原文件，不按场景截取；快照内容哈希和来源哈希均为完整原文件的 SHA-256。数据库行号和本机绝对路径不写入 Scenario。

Runtime 的 `DataCatalog` 不依赖 Qt，提供目录查询、EOP 安装、finals2000A 原文件导入、偏好保存和按 `DataLock` 精确解析。每次加载核验清单、内容文件及时间依赖身份；当前只支持 EOP/内置时间这一组依赖。SQLite 使用 WAL、写事务和忙等待，串行化多个进程的发布；先验证临时副本、发布文件，再提交索引。启动时可恢复已发布而尚未写入数据库的有效快照，未发布临时目录不进入列表。这里不承诺断电时所有文件与数据库跨介质原子持久化。

多个场景共用相同文件，不各自复制数据。启动时按原身份导入附带快照及旧 `%LOCALAPPDATA%/OrbitForge/eop` 目录；原目录保留，迁移不改变既有项目的数据锁。重复导入幂等，已有损坏文件不会被新导入静默覆盖。损坏用户条目在窗口提示并排除加载；内置版本仍可从应用资源读取。第一版保留所有已安装快照，不自动删除历史版本。跨电脑项目可能未登记在本机目录中，不能简单把“当前无引用”当作可永久删除的证据。

## 全量下载与自动更新

入口为“数据 → 数据中心”，无需打开场景即可使用。默认界面只有数据状态、一个“下载完整数据／检查并更新”按钮和“自动更新数据”开关；不选择日期、不显示三种更新策略。版本列表、哈希、UTC 数据有效期、来源、目录、手动导入与场景应用放在默认收起的“版本与场景引用”中。

自动更新默认勾选，但首次完整下载由用户启动。已有完整文件后，仅在应用运行期间每分钟检查是否距上次尝试满 24 小时，不增加常驻服务。用户可关闭自动更新或随时手动更新。关闭窗口后下载继续，退出应用会中止。进度、结果和失败原因在窗口显示，最近状态持久保存；失败后的自动重试遵循相同间隔。

成功安装后保存该来源的 ETag 和 Last-Modified。再次更新使用条件请求：收到 304 时不传输文件正文、不新建快照；收到 200 时校验完整文件后发布。条件头仅对应已安装且已验证的原文件，不在失败或仅收到响应头时推进。来源不支持条件请求时，完整获取后按 SHA-256 去重。这里没有承诺字节级增量传输，也不把不完整的 daily 文件拼接为历史版本；网络优化不改变完整文件身份和 Scenario 可复现性。

下载先进入 staging，使用 HTTPS、系统证书验证、不降级到 HTTP 的重定向、30 秒无活动超时、120 秒总时限和 16 MiB 大小上限。完成后校验传输结果、文件格式、完整逐日覆盖、数据数值及时间依赖，再发布快照。成功、失败或取消时清理本次下载临时文件；进程被强制终止时可能留下不参与加载的 staging 文件。不会把半成品标记为已安装，也不修改已有场景。Windows 便携包携带 Qt TLS 后端。

当前下载源为 [IERS finals2000A](https://datacenter.iers.org/data/9/finals2000A.all)。导入后的 ID 由全文件内容哈希构成，重复下载同一内容不会产生重复版本。原文件中的历史记录和不完整预测尾部全部保留；可计算范围取连续完整的 x/y、UT1、dX/dY 记录与时间 Provider 有效期的交集。缺字段的尾部不补零、不外推；中间缺日、重复日、错误日期、部分缺损字段和非有限数拒绝安装。Bulletin A 的历史支持从 1972 年后的有效 UTC 起，不沿用 C04 的 1984 年限制。列定义以 [USNO 说明](https://maia.usno.navy.mil/ser7/readme.finals2000A)为准。

因此“完整文件已下载”与“任意未来日期可计算”是不同条件。界面显示实际可计算范围；UTC 超出内置时间数据有效期仍明确拒绝。未来时间数据更新必须加载并验证新的原文及规则，不能只延长旧表有效期。

## 缺失数据

当前打开项目只接受已安装或附带的精确版本，缺失时保留原场景并报告错误；已具备完整依赖的项目可离线打开。缺失版本的自动定位/下载尚未实现。后续 resolver 可根据用户策略获取原版本，下载后必须匹配项目记录的内容和配置哈希。如果上游只保留最新文件，不能用它替代旧引用，应提示导入原快照或显式更新场景数据。

后续可增加“导出项目及依赖包”，携带 `.orbitforge` 文件、固定清单和所需文件。它复用相同数据锁，属于可移植性功能，不改变统一数据目录的默认工作方式。

## 开发顺序

1. **已完成：** 数据引用值、规范哈希、Scenario 绑定、项目 v3 持久化、旧文件升级和一致性验证。
2. **已完成：** SQLite 目录、文件去重、EOP 数据锁解析、统一窗口、旧目录迁移；验证两场景共享文件且独立固定版本。
3. **已完成：** finals2000A 全文件适配器、原文件导入、手动更新、HTTP 条件更新、取消与失败重试。C04 当前仍通过已有清单导入。
4. **部分完成：** 应用运行期间的自动检查/下载已实现；下一步实现按实例加载的时间 Provider，并处理精确旧版本的缺失依赖下载。
5. SPICE 和轨道目录适配器、项目依赖包、容量与历史版本管理。

各增量都保留离线使用能力。验收重点是身份可核验、场景可复现、更新可取消，以及任何下载或应用失败都保留已有可用版本。

## Python 示例

```python
import orbitforge as of

catalog = of.DataCatalog('local/shared-data')
entry = catalog.install_eop('snapshot/manifest.json')
# 也可直接安装完整原文件，自动推导可计算范围，不需要手工准备清单：
# entry = catalog.import_finals('finals2000A.all',
#     'https://datacenter.iers.org/data/9/finals2000A.all', '2026-10-10')
project = of.load_project('mission.orbitforge')
provider = catalog.resolve_eop(project.data_lock)  # 只接受该场景固定的版本
print(entry.lock_sha256, len(catalog.snapshots))
```

`ORBITFORGE_WITH_DATA_CATALOG` 默认关闭，图形桌面预设和标准 wheel 显式启用。关闭时 `data_catalog_available()` 返回 false，构造目录明确报告功能不可用；普通 headless 构建保持无 SQLite 依赖。
