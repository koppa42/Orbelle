# OrbitForge 开发者规范

本文面向参与 OrbitForge 编码、测试、评审和维护的开发者，约定模块职责、实现边界、验证方法与提交标准。项目当前处于开发预览阶段，允许大规模重构；架构调整应同步处理受影响的调用方、数据格式、测试和文档。

## 1. 开始开发

1. 阅读 [README](../../README.md)，了解当前能力与限制；按[构建说明](build.md)准备对应功能的依赖和构建预设。
2. 阅读[模块契约](../architecture/p0_contracts.md)及待修改模块的设计文档，确认代码归属、输入输出和已有测试入口。
3. 从最新 `main` 创建主题分支，所有改动均通过 PR 进入 `main`。禁止直接推送 `main`，文档、测试、CI、依赖更新和紧急修复同样适用。围绕一个明确目标组织改动，说明用户可观察到的行为及验收方式。
4. 跨模块重构、算法替换或文件格式调整，应先说明依赖变化、兼容策略和验证方案，再按可检查的增量实现。

本机路径和工具链选择放入 `CMakeUserPresets.json` 或当前进程环境。公共配置必须能够在其他开发机和干净的 CI runner 上使用。

## 2. 模块职责与依赖

| 位置 | 职责 |
| --- | --- |
| `modules/core` | 物理量、时间、状态及基础接口；只依赖 C++ 标准库 |
| `modules/results` | 拥有自身存储的计算结果、时间序列和带类型表格 |
| `modules/application` | Session、Scenario、Project 及报告定义等应用模型 |
| `modules/providers` | ERFA、IERS、CSPICE 等具体计算与数据适配 |
| `modules/runtime` | 装配 Provider，提供桌面、SDK 和 Python 共用的功能入口 |
| `modules/visualization` | 结果到显示快照的转换，不依赖窗口或图形库 |
| `modules/render_vsg`、`modules/geo_rocky` | 渲染、地球显示及图形资源适配 |
| `apps/desktop` | Qt 窗口、交互、后台任务调度及工作区装配 |
| `bindings/python` | Python 绑定、包入口、类型声明与接口测试 |

- 保持依赖方向：Runtime → Application → Results → Core；Visualization 使用结果，具体 Provider 实现 Core 接口。
- Core 和公共计算类型中不引入 Qt、Python、VSG 或 Rocky 类型。Application 通过接口使用计算能力，由 Runtime 选择具体实现。
- 新增计算或报告能力应进入可复用模块。桌面和 Python 调用同一套实现，避免各自维护一份算法。
- 计算结果与显示缓存分离。地图插值、轨迹简化和像素降采样只影响显示，不得成为分析、报告或导出的计算输入。

## 3. 代码与接口约定

- 使用 C++20，CMake 最低版本以根配置为准。代码需兼容 CI 声明的 Windows/MSVC 和 Linux 工具链。
- C++ 格式遵循根目录 [`.clang-format`](../../.clang-format)：LLVM 基础样式、4 空格缩进、100 列。命名和文件组织沿用所属模块的风格；格式化范围限于相关改动。
- 资源生命周期应明确，文件、线程、Provider 和 GPU 对象在正常、异常及取消路径上都能正确释放。不要通过未说明的全局可变状态共享计算输入。
- 公共接口注明单位、参考系、时间标准、有效范围、所有权和失败行为。参数或数据无效时明确返回错误，不伪造可用结果。
- 新增或修改对外能力时，同步检查 C++ 导出接口、Python 绑定、`_native.pyi`、相关示例及接口文档。
- 开发阶段可以调整 API 和文件结构，不要求兼容旧项目格式；不兼容改动必须说明影响，并明确拒绝非当前格式。当前 SDK 未承诺稳定 ABI。
- 注释用于解释模型假设、边界条件、生命周期和必要的取舍；复杂行为优先通过清晰的类型与职责划分表达。

## 4. 数值计算约定

- 计算 API 使用 SI 单位，长度为米、速度为米每秒、角度为弧度。界面单位转换在输入输出边界显式完成。
- `Epoch` 使用 `int64` TAI 纳秒，零点是 **2000-01-01 12:00:00 TAI**。不要将其与 J2000 TT、UTC 文本或浮点秒混用；时间运算检查溢出和纳秒精度。
- 状态必须保留历元、原点和参考系。GCRF / ITRF 的完整状态变换包含旋转引起的速度项；SPICE J2000 状态也不能仅凭数值单位相同而当成 GCRF 状态。
- 算法实现应列出模型假设、参数来源、适用范围和已知限制。区分瞬时根数与平均根数、椭球高与其他高度基准、采样统计与连续区间极值。
- 涉及模型或精度判断时，优先依据官方资料和原始文献。与 STK 或其他工具比较时对齐模型、输入、时间、参考系和数据，记录仍存在的差异。
- 数值验证覆盖解析案例或独立参考、边界条件及错误输入。容限需要依据，不能通过放宽容限掩盖回归。

详细约定见[时间与参考系](../architecture/time_frames.md)、[CSPICE](../architecture/spice.md)、[J2](../architecture/j2.md)与[验证方法](../validation/README.md)。

## 5. 数据、任务与持久化

- 数据由统一目录管理；计算 Provider 使用明确注入的数据，不隐式联网或读取桌面偏好。下载与自动更新由上层管理。
- 计算开始时捕获不可变输入、Provider 和有效策略。后台更新不得改变运行中的计算；任务完成后检查修订，丢弃已过时的结果。
- 打开或重新计算场景时，比较当前数据与项目记录。数据或实际使用的策略变化须经用户确认；拒绝则停止该操作，保留原场景。
- 覆盖不足时报告所需范围、可用范围和处理入口。有限 EOP 外推遵守显式设置和上限，不延长 UTC / 闰秒表的有效期。
- 数据引用记录内容与解释配置的哈希。下载时间、最近检查时间和本机路径等管理信息不应改变计算身份；普通项目打开流程不强制保留旧数据文件。
- 下载、导入、场景重建和文件保存遵循“准备 → 校验 → 发布”。失败或取消时保留原有可用文件和活动场景，避免部分结果混入。
- 存储格式可以按需求设计。开发预览阶段 `.orbitforge` 只维护当前格式的读写实现，不增加历史格式解码、迁移器或按旧版本补默认值的分支。结构或语义变化时递增版本，替换当前读写定义、固定样例和文档；非当前版本明确报错，保留源文件和活动场景。修改项目格式或数据清单时，同步验证版本、完整性和跨 C++ / Python 的读写一致性。
- 固定参考数据的原始字节属于验证输入。更换数据时核对来源、散列、有效期及边界测试，并遵守 [`.gitattributes`](../../.gitattributes) 的字节保留规则。

实现前阅读[数据中心](../architecture/data_center.md)、[数据引用](../architecture/scenario_data_lock.md)和[项目文件](../architecture/project_files.md)。

## 6. 桌面与交互开发

- 复用现有主题、单位控件、历元编辑器、工作区和对象操作流程。已有对象的选择统一使用可搜索的“对象选择窗口”，按业务限制候选类型，避免使用随对象数量增长的下拉框；参数和对象类型等固定枚举仍可用下拉框。新界面的字体、间距、对齐、图标和状态反馈应保持一致。
- 界面以清爽、易读和专业工具的操作效率为准，可保留克制的二次元视觉气质。优先整理信息层级，减少拥挤表单、重复说明和多余折叠。
- 布局根据面板实际可用宽度调整，使用 Qt 逻辑像素；窄分屏与浮动窗口同样适用。表单可从并排改为上下排列，导航可改为紧凑页面切换，内容使用内部滚动并保持主要操作可达。不要仅靠隐藏横向滚动条掩盖超宽内容。
- 尺寸变化只调整布局，不重建编辑器、重算数据或重新挂接原生图形窗口。保留未应用输入、单位、对象选择、当前页面、报告结果及用户调整的分隔条位置；恢复宽布局时不反复重置分屏。
- 耗时计算、下载和资源准备放入后台，提供进度与取消。GUI 线程负责交互和发布结果；任务不得持有已经失效的窗口对象。
- 编辑草稿、应用修改和保存项目的边界必须明确。取消、关闭或任务失败时，不得误提交草稿或丢失已存在的有效状态。
- 对象操作使用稳定 ID。二维、三维、对象树与报告中的选择和绑定保持一致；纯显示修改不改变物理输入。
- 实际检查窄分屏、不同 DPI、键盘焦点、选中与悬停、文本截断及错误状态。修改交互时同时检查取消、重开和对象删除等路径。
- 报告与曲线复用相同计算结果；具体对象范围、模板与导出行为遵循[报告契约](../architecture/reports.md)。

图形窗口、后台编译与 GPU 资源的生命周期调整须遵循[图形集成约定](../architecture/graphics.md)，并执行对应的真实 GPU 验证。

## 7. 按改动选择验证

本地日常开发只需使用 **Python 3.13**；其他 Python 版本由 CI 验证。当前 Windows / Linux 矩阵覆盖 3.11–3.15，版本范围统一维护在 `pyproject.toml`，不要在脚本中另建一份清单。

| 改动类型 | 至少需要的验证 |
| --- | --- |
| 数值模型、时间、参考系 | 对应 C++ 单元与集成测试、边界测试；按协议核对参考值或不变量 |
| 项目文件、目录或导入器 | 往返读写、损坏与越界输入、版本行为、失败后原状态保留 |
| 公共 API / Python | 更新绑定和类型声明；编译扩展，在独立环境运行相关 API 测试与示例；涉及包结构时另做 wheel 安装验证 |
| 桌面控件与工作区 | 相关 Qt offscreen 测试，以及实际布局、状态和交互检查 |
| 渲染、窗口或 GPU 生命周期 | 对应图形 smoke、验证层及真实 GPU 检查；性能变化按固定协议比较 |
| SDK、依赖或打包 | 安装或迁移后的 SDK 消费端；脱离开发目录的运行库、插件与资源检查 |
| CI / 发布脚本 | 相关脚本测试、工作流检查与实际 CI 运行结果 |

修复可自动验证的行为缺陷时，优先补充能复现问题的回归用例。纯文案和简单视觉调整按实际风险检查；测试应验证行为和契约。

完成相应依赖配置后，使用仓库已有的预设，例如：

```powershell
cmake --build --preset astronomy
ctest --preset astronomy

cmake --build --preset desktop-graphics
ctest --preset desktop-graphics
```

选择与改动相关的入口执行。首次配置、Python 安装验证及图形验证的完整命令见[构建说明](build.md)。Qt offscreen 检查不能替代真实 Vulkan 呈现与性能验收。

验证结果应记录实际执行的命令、环境、输入和结论。日志、截图及报告写入新的 `out/validation/<运行名称>/`，明确区分已通过、失败和未执行的项目。

## 8. 依赖、CI 与发布

- 第三方依赖通过 `vcpkg.json`、固定基线和 `cmake/ports/` 管理；Python 构建依赖在 `pyproject.toml` 中声明。升级时检查兼容性、许可和交付影响。
- 显式声明功能依赖，避免开发机上的完整安装掩盖缺项。例如桌面需要 PNG/JPEG 与联网能力，离屏 UI 测试需要对应平台插件。
- 保持可选功能的边界。基础无界面构建不应因桌面改动而新增 Qt、VSG 或 Rocky 依赖。
- CI 复用编译依赖，Python 矩阵只重建各解释器的扩展；标签流程才构建对应 wheel。修复 CI 时检查完整日志和最终汇总，不能仅以本地构建成功代替远端验证。
- PR 合并前更新到最新目标分支并确认当前提交的 **CI passed** 成功；后续提交或目标分支变化后，应重新取得相应检查结果。代码 PR 执行两平台及完整 Python 矩阵测试；代码合并后验证 C++、桌面和基准 Python，不重复其他 Python 版本。纯文档 PR 和纯文档合并仅执行明确允许的轻量检查；差异范围无法确认时保留原生测试。
- 完整 Release 数值回归及精度容限保留。PR 的常规 ASan/UBSan 单独并行运行，默认覆盖新增用例；全量插桩仅手动触发，合并后不重复 sanitizer，不配置定时任务。分层规则与手动入口见 [CI 与版本发布](ci.md)。
- 正式交付包含 Windows 便携包、Windows/Linux C++ SDK 和 Python wheel，以及校验值。包内应包含必要运行库、插件、资源和第三方许可。
- PR 和 `main` 只编译、测试，不生成便携 ZIP、SDK 发布归档或 wheel。作业间仅传递已编译依赖，另保留诊断日志；只有版本标签流程构建发布包，进行安装与迁移验证并上传发布附件。
- 推送匹配项目版本的 `vX.Y.Z` Git 标签触发发布，标签提交必须已经进入 `main`，检查全部成功后才公开 Release。版本标签禁止修改和删除，修复通过 PR 和新版本交付。清单版本通过 `tools/ci/version.py` 统一维护。

平台范围、CI 环境和具体发布步骤以 [CI 与版本发布](ci.md)为准。

## 9. 文档与 PR 要求

- 完整流程为“主题分支 → 提交与推送该分支 → 创建或更新 PR → 当前提交 CI 通过 → 维护者确认合并”。不得直接推送或强制更新 `main`，也不得绕过分支规则。
- “提交并推送”只授权更新主题分支和创建或更新 PR，不代表授权合并；“检查能否合并”是审阅请求。自动化工具或代理只有取得维护者明确授权后才执行合并。
- 行为、接口、格式或构建步骤发生变化时，同步更新对应文档与示例。架构文档描述当前契约，并明确实现范围和已知限制。
- 仓库只保留源码、配置、可复现的测试与验证方法、必要固定输入和运行资源。逐次日志、截图、开发记录、源码副本、缓存和发布包保存在 `out/` 或 `local/`；不使用强制添加绕过忽略规则。
- 插画资源无需额外创作过程或提示词说明；第三方资源继续保留必要的来源与许可。
- PR 说明应包含：解决的问题、最终行为、关键设计或兼容影响、实际验证及未覆盖范围。界面改动附必要的前后对比；数值改动注明参考依据与容限。
- 一个 PR 围绕一个完整目标，避免混入无关格式化或清理。重构可以跨模块，但应能清楚说明每部分为何需要改变。
- 合并方式按 PR 约定执行，保持历史清晰；涉及已发布历史的重写或强制推送时，先与维护者明确范围。

提交前检查：

```powershell
git status --short
git diff --check
git diff --cached --check
git diff --cached --stat
```

同时审阅暂存文件的具体差异，确认没有本机绝对路径、凭据、生成产物或无关文件。

## 10. 交付完成标准

- [ ] 功能、取消与失败路径符合约定，原有可用状态得到保留。
- [ ] 模块依赖、公共接口、绑定、类型声明和持久化行为保持一致。
- [ ] 必要验证已执行，结果可追溯；未验证的范围已明确说明。
- [ ] 文档与示例反映最终行为，提交内容完整且聚焦。
- [ ] 待合并提交的 CI 通过；涉及交付时，已验证安装或解压后的使用方式。
